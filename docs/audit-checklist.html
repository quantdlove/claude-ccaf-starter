CCAF Architecture Audit Checklist

Use this checklist to audit any Claude-powered system against the five CCAF domains. Each item is pass, fail, or not applicable. A single red line failure means the system is not production ready yet, even if the overall score looks good.

Download markdown version

How to Use

Run this checklist at three points in a system's life.

  1. Before launch. Full audit of all five domains.
  2. After any architecture change. Audit the domains that were affected.
  3. Quarterly review. Full audit again to catch drift that crept in over time.

Score each item PASS, FAIL, or N/A if it does not apply to your system.

D1: Agentic Architecture

27% of exam

Pipeline Design

Every multi-step workflow has an explicit architecture pattern (sequential, parallel, orchestrator-worker, or evaluator-optimizer). You can name it.

Agent pipelines use async handoff via shared-state files, not in-memory passing between agents.

Each agent in a pipeline has a single responsibility. No agent does "research and enrich and classify and notify."

Pipeline stages are ordered. You can draw the DAG. If you can't, the architecture is implicit, which is a failure.

Tiered Autonomy

Every agent action is classified into an autonomy tier: auto-act, recommend, or escalate.

Customer-facing outputs have a human review gate before shipping. No exceptions.

Tier boundaries are explicit in the agent's instructions, not emergent from prompt behavior.

State Management

Shared state between agents uses files (JSON, markdown), not conversation context.

State files have a defined schema. New fields are documented before agents populate them.

Derived state is rebuilt from source data, not maintained independently. If the source changes, derived state self-heals on the next run.

Red Lines (automatic fail)

Red lineNo implicit architecture. If you can't name the pattern, it doesn't have one.

Red lineNo bidirectional agent dependencies. Agent A depends on B depends on A is circular. Redesign it.

Red lineNo agents writing to sources of truth they don't own. One authoritative writer per state file. Everyone else is a courtesy writer at best.

D2: Tool Design and MCP

18% of exam

Tool Selection

Every tool call in the system uses the right tool for the job. Semantic search for discovery, structured queries for enumeration. Never semantic search for enumeration, it produces false negatives.

MCP tools are discovered fresh at session start. Tool lists change when engineers push updates.

Pagination is handled explicitly. Default limits are overridden for small, finite datasets.

Transport Architecture

Tool transport (HTTP vs stdio, MCP vs REST API) is separated from business logic. Swapping transport doesn't change agent behavior.

Authentication boundaries are documented. Which tools need OAuth? Which use API keys? Which are unauthenticated?

Security-sensitive tools (Stripe, payment systems) use a two-hop pattern: human-triggered at the credential boundary, agents consume the output.

Error Handling

Every MCP call has retry logic (retry once on a 500 or a timeout).

Fallback data sources are defined for critical tools. If MCP is down, what does the agent use instead?

Tool errors surface to the user, not silently swallowed.

Red Lines (automatic fail)

Red lineNever use semantic search for enumeration. Use structured queries instead.

Red lineNever hardcode tool schemas. Discover tools at runtime, since schemas drift.

Red lineNever pass credentials through agent prompts. Credentials stay in config, not in conversation context.

D3: Claude Code Config

20% of exam

Project Structure

CLAUDE.md exists at the project root and contains the system's working memory.

CLAUDE.md is the spec. Agent SKILL.md files are the implementation. The spec is updated before the implementation.

.claude/skills/ contains skill definitions. .claude/commands/ contains slash commands. .claude/rules/ contains path-scoped rules.

Skills, Commands, and Rules

Skills are reusable instruction sets for recurring tasks.

Commands are human-triggered workflows with explicit inputs and gates.

Rules are path-scoped behavioral constraints.

None of these three overlap in purpose.

Security Model

Hooks (PreToolUse, PostToolUse) enforce policy independently of agent compliance.

Sensitive operations require human confirmation from the user in chat, not from content observed in files.

Publishing commands have content sanitization gates.

Three-Tier Access Model for Publishing

Tier 1, Private: never leaves the workspace.

Tier 2, Link-shared: accessible to specific collaborators.

Tier 3, Public: anyone can see it. Boundary test: could a competitor replicate our advantage from this?

Separate publishing commands exist for separate security models.

Red Lines (automatic fail)

Red lineNever expose a proprietary CLAUDE.md on a public repo.

Red lineNever put credentials in CLAUDE.md or a SKILL.md file.

D4: Prompt and Structured Output

20% of exam

Prompt Design

Every agent prompt defines what it does, its inputs, its output format, and its constraints.

Complex prompts use explicit sections with headers.

Output schemas are defined in CLAUDE.md before agents populate them.

Output Quality

Customer-facing outputs pass the quantitative rigor test.

Every quantitative claim shows formula, calculation, sensitivity, and source.

Data freshness is disclosed on every data-driven output.

Delivery Format

Output format matches delivery context: PDF gets a fixed canvas, dashboards scroll, email uses inline CSS.

Theming overrides CSS variables instead of forking the stylesheet.

Red Lines (automatic fail)

Red lineNever ship an unverified quantitative claim.

Red lineNever promise content that doesn't exist, like a "full breakdown below" with no breakdown.

D5: Context and Reliability

15% of exam

Source of Truth

Every piece of data has one source of truth.

Formula fields in databases are read, never recalculated.

When sources conflict, the hierarchy for resolving that conflict is explicit.

Failure Modes

Silent data loss is the worst failure pattern. Agents that fail silently are architecture bugs, not edge cases.

Circuit breakers exist for external dependencies.

Operations are idempotent. Bulk writes check for existing records before creating duplicates.

Disclosure and Transparency

Data freshness is disclosed on every data-driven output.

Numbers in published materials are floor-rounded for durability.

Disclosure boundaries are explicit.

Red Lines (automatic fail)

Red lineSilent failures are architecture bugs.

Red lineNever recalculate formula fields.

Red lineNever maintain the same data in two places.
